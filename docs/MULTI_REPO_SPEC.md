# Multiple repositories in one project

Version 0.2.0 implements independent repository collection and project composition. Independent QA found gaps in cross-repository work, legacy adoption, configuration editing and MCP freshness; these six reproduced defects have local regression fixes. The user selected manual recovery for interrupted updates; persistent backup locations, Finder instructions and Homebrew reinstall commands are now implemented. Decision: collect repositories independently, then compose one project view (A). This keeps successful repositories usable when another repository is unavailable. A single analysis of every checkout was considered; it couples refreshes and failure recovery.

## User behavior

Agent session discovery, activity tracking and session resumption are outside the product scope. Git worktrees and uncommitted source changes remain part of repository impact. Legacy session fields are omitted at the shared read boundary; stored snapshots are not rewritten to remove them.

- Create a project with one repository; add related repositories without replacing earlier maps. Register either a GitHub URL or an existing local folder, then choose all repositories or one. URL connections clone code and run their first collection; opening the resulting project does not trigger an extra automatic refresh of existing repositories.
- Each repository has a stable ID, a local Git repository, development/production refs, and frontend/backend source roots. A role may be absent; two roles may intentionally use the same ref. Frontend-only, backend-only and general repositories are valid. The automatic parser retains its framework-specific coverage. Users chose explicit AI analysis instead of maintaining additional framework parsers: ai_extract.py accepts analysis from any connected MCP agent and returns the same map schema. The agent uses its own model; the server exposes commit-pinned source reads and verifies submitted results. CLI commands prepare requests for the connected agent. Missing configured source directories are reported; framework-specific entry filenames are not required.
- Show repository names on screens, requests, GitHub work and evidence. Preserve original paths separately from internal identifiers. Equal screen paths, function/file names, PR/issue numbers, and table names in different repositories remain distinct. Mobile folding and common-component detection remain local to each repository.
- Automatic cross-repository HTTP matches are candidates. Only an explicitly configured API destination can connect matching mounted requests; ambiguous matches stay candidates. Mark configured connections as configured, never as code-proven. Tables are separate unless explicitly mapped to a shared data ID.
- Refresh all repositories or one. Preserve the last complete successful snapshot on fetch, extraction, GitHub, or publication failure. Show last attempt, last success, error and retained commit per repository. A first failure is not an empty success. Serialize refresh/configuration/AI/test writes with a project lock. Publish completed repository snapshots atomically.
- Changing refs/layout starts a new comparison baseline rather than reporting all old items as deleted. Unregistering a repository keeps its stored snapshots. Existing single-repository files remain readable and are preserved on adoption.
- UI and MCP read the same composed snapshot. Repository selection has stable IDs and cannot be overwritten by older asynchronous responses. Cross-repository dependencies remain visible with their source repository.
- Code-map AI actions and test-rule/evidence writes require an explicit repository in a multi-repository project. Change explanations may cover the full project or one repository, keeping repository IDs, PR base branches and each comparison window explicit. Existing single-repository calls keep working. Test evidence is checked against that repository's recorded commit. Ambiguous MCP targets return choices rather than silently selecting the first.

## Storage and implementation

`project.json` describes the project and its repositories. Project-level `briefing.json` retains independently keyed repository/branch/language explanations and the evidence used by each successful result. Inputs come from the last successful collection; changed inputs, settings or code reject late results. Preparing, recording and reading explanations do not run collection or advance change history. App-driven execution and direct model APIs remain separate follow-up issues. Each repository retains the current JSON formats in its own immutable generation. A single atomic repository-state file selects successful generations and reports attempts. Failed or interrupted generations never replace the selected successful generation. Legacy files are referenced in place until a successful new generation exists.

`connections.py` parses GitHub URLs and manages full-history clones without a checkout under `<project>/.code/<URL hash>/repository`. HTTPS, HTTPS `.git`, Git SSH notation and owner/repository normalize to one HTTPS URL; duplicate URLs and invalid forms are rejected before download. The user selected managed clones over API-only source reads to reuse Git-based analysis. The cost is local disk usage and download time. The existing remembered-account environment authenticates clone and refresh without changing global login state. Authentication failures expose account selection in the same registration form. A clone is staged before publication; failed downloads preserve existing configuration and can be retried. Disconnecting retains code and maps; reconnecting reuses code after verifying its URL and ownership marker. Managed storage is excluded from user worktree reporting. Its remote default branch pointer is updated after each fetch; explicitly configured refs/layout remain unchanged. Existing local folders retain their worktree reporting and are never deleted.

`app_control.py` adds standard MCP live-control tools (`app_state`, `app_targets`, `app_control`, `app_command_result`). The user selected a named local app-command bridge over navigation links and GUI automation for bidirectional selection and full action coverage. The macOS app owns a private Unix socket (0700 directory, 0600 socket); no HTTP listener or external server is used. Its native mailbox serializes commands, scopes IDs to an app instance and retains replay tombstones after response eviction. Only the UI can acknowledge application. Queued/running commands are incomplete; UI reload interrupts unresolved commands with unknown effects, and old instance IDs cannot run in a new app. Closed, not-ready, missing, expired and failed results remain distinct.

`ui/control.js` derives stable target identities from screens, requests, programs, data, jobs, connection content and visible feature-group members, independent of display indexes. SHA-256 revisions cover the displayed map, analysis and configuration. Selection requires explicit project/repository/branch/target/revision; stale revisions and missing targets return errors. Commands reuse UI/native paths for navigation, selection, relations, source details, request steps, configuration/shared data, GitHub identities, collection, analysis preparation/result reads, language/comparison preferences and update actions. The existing analysis record tools store submitted model results. Request preparation returns prepared=true/executed=false. Starting an update returns started=true/completed=false; update state reports its progress. Model execution remains the separately scoped app-execution follow-up. Result reads retain comparison history and its selected entry; navigation does not collect. No chat history is collected.

`project.py` owns validation, registration, locking, snapshot publication, composition and command dispatch. `mapcore.py` and the Tauri bridge consume its bundle reader; they do not implement separate composition rules. The composed compatibility view uses repository-qualified internal keys and retains `repository` and `source_*` fields for original paths. It also includes repository metadata and HTTP candidate/configuration provenance. A filter changes the visible source screens/work while retaining their dependency targets.

Refs and layout are passed to the existing collectors through an explicit child environment. GitHub failures are errors, not empty lists. Source readers accept absent application halves. Existing user checkouts, branches, worktrees and working files are preserved; collection may run `git fetch`. Managed app storage also updates its `origin/HEAD` pointer.

The 0.2.0 app also adds Homebrew updates from the UI. It validates the managed app path and available version before closing. A native executable copied outside the app holds an inherited OS lock, waits for the parent to exit, backs up the complete app, runs the cask upgrade, verifies the installed version, and starts the new app. Only the expected app path and version can acknowledge startup. Failed installation or startup triggers recovery; partial backups never replace the original app. A restored app whose Homebrew receipt is newer uses reinstall on retry. Failed recovery keeps its files and reports their location. App collection and AI actions cannot overlap the update in the initiating app. ZIP/source builds use the manual fallback.

The packaged backend allowlist must include `project.py`. Python source/layout/test rules participate in extraction invalidation. The UI offers project/repository setup, repository selection, status and qualified evidence links in Korean and English. MCP tools accept an optional repository scope and share the UI's results.

The UI prepares a copyable request for the user’s connected MCP agent. MCP `analyze` returns instructions/schema and arguments; `analysis_source` supplies pinned source without requiring local filesystem tools in the client; `record_analysis` validates and publishes the submitted JSON. No AI provider is launched by this default path. Repository, role, language, commit and configuration fingerprint scope the exchange, and changed commit/configuration submissions are rejected. Grouping, architecture, program jobs and request steps use `request_ai_task` and `record_ai_task` with the same connected-agent model. Their UI buttons and compatibility CLI commands prepare requests without launching an AI CLI. Submitted task output is validated against its immutable source and stored input snapshot; changed input is rejected. Each branch map stores its own `task_outputs`; UI branch switching and MCP queries choose that role’s results. A manually authored system is retained and an AI proposal is stored separately as `system.ai`. System nodes, links and external services require source evidence; unknown facts are normalized to the existing `{text, needs}` format. Request steps retain their route identity and branch; job triggers must belong to the selected program’s code, and producer-route links remain AI interpretations. This reuses the established request/source/record exchange rather than maintaining executable adapters for each agent. Ordinary refresh retains AI maps and marks changed commits as requiring analysis without invoking AI. Repeated CLI requests do not mutate stored maps or launch AI; connected agents control their own model usage. AI items require tracked files, exact source lines and literal quotes; malformed output cannot replace the selected generation. These checks establish text provenance, not semantic correctness or exhaustive coverage. Unknown areas and AI origin are shown in UI/MCP. Each AI route stores its own commit-specific flow, avoiding steps from a different branch. Test rules and recorded evidence use one shared deterministic matcher for static and AI maps; refresh updates those links without another AI call.

Independent QA initially ran 36 Python tests (including the prior built native helper/runtime) and 16 Rust tests successfully, then found six defects outside those regressions. Six added Python regressions and one Chrome save regression failed before source fixes and pass afterward. The multi-repository suite now has 29 tests, including custom non-Python source roots; 18 AI-specific tests cover the new analysis path. The app was rebuilt with these fixes, its project.py and mcp_server.py match source, and all 64 Python tests including the native helper and relocated runtime pass against that build. Independent reviewers confirmed the six fixes, including backend-only file/HTTP/table work queries. Interrupted update recovery now uses manual guidance rather than a persistent recovery service; this adds no login or background service. Backup copies live under the app data directory, outside temporary helper staging. Before replacement, the existing log and state files record their location, original destination and a shell-quoted Homebrew reinstall command. Successful update/rollback removes that attempt’s backup; interrupted or failed recovery retains it. Validation uses 29 multi-repository regression tests, 18 AI-analysis tests, 17 packaging tests (including the native helper and built runtime), 18 Rust tests, the design-token checker, and browser checks for projects, language and updates. The collector integration executes the actual Python collectors with temporary synthetic git/GitHub responses. Browser checks mock the native bridge; the relocated-runtime check uses the real MCP protocol. The native update integration substitutes only Homebrew and the original parent process: helper copying, inherited locking, replacement of a disposable app, startup and acknowledgement use the built native executable. No installed app or real Homebrew package is upgraded. Run it with `WHERE_WERE_WE_UPDATE_APP=/path/to/where-were-we.app src-tauri/runtime/python/bin/python3 -I -B -m unittest discover -s tests -p test_packaging.py`; set `WHERE_WERE_WE_RUNTIME` to the app’s `Contents/Resources/runtime` to include the relocation checks. A mutation disabling the managed-app path check fails its regression test. A mutation restoring the former mobile-key collision makes its regression test fail. Forcing task readers to select development results for both roles fails the branch-separation assertion.

Real company repositories, production systems, private project maps, complete native-window interaction and end-to-end sessions in individual MCP clients were not tested. The default connected-agent path is verified with the standard MCP protocol. AI tests block real AI calls and use synthetic agent-submitted JSON; a standard stdio MCP client exercises request/source/record without Claude on PATH; parsing, pinned Git reads, validation, isolated CLI execution, snapshot publication, composition and runtime packaging use actual code. A mutation disabling literal quote validation fails its regression. Normal refresh rechecks HTTP patterns and recorded test evidence without another AI call, including dynamic URL normalization shared with static extraction. The ARM macOS app was built locally as 0.2.0 with an ad-hoc bundle signature, without Developer ID signing or notarization. The release ZIP was extracted into a temporary path and its actual native window was confirmed. This does not verify Gatekeeper approval at an installed path. The release ZIP and Homebrew definition use the same version and archive checksum.

Atomic publication applies to configured projects. Legacy files remain readable; adopt them into a configured project to use the new per-repository transactions. Repository refreshes have independent commit/timestamp boundaries, so a composed view is not a simultaneous snapshot across repositories.

## Advanced configuration

The app edits repository paths, refs, source roots, API targets and shared-table mappings. The existing repository dialog adds/removes shared groups and repository/table members, preserves unsaved values when repository rows change, and suggests collected tables. No target DB is queried or changed. The same configuration remains available through `project.json` or `project.py configure`. For example, this fragment explicitly connects the two table identities:

```json
{"shared_data":[{"id":"workspace","members":[{"repository":"api","table":"settings"},{"repository":"worker","table":"settings"}]}]}
```

Use existing repository IDs in the members. Pass the complete project configuration to `project.py configure PROJECT` on standard input; the fragment alone does not replace a complete configuration. Shared identities are user assertions, not proof of a shared database.
