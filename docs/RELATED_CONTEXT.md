# 관련 컨텍스트: 요구사항과 ADR

상태: 제품 방향과 아래 확정 결정은 합의됨. 기능 구현과 동작 검증은 시작하지 않음.
기록일: 2026-11-02
기준 코드: `670e31d3ea2e3766cce890f0198d92532771c868`
작업 브랜치: `feat/related-context`

이 문서는 관련 컨텍스트 기능의 요구사항과 결정 기록을 관리하는 정본이다.
PR 본문은 변경 요약과 이 문서의 링크만 유지한다. 구현 과정에서 이 문서의 해당 항목을 갱신한다.

## 해결하려는 문제와 목적

새 AI 세션마다 서비스의 사용자, 목적, 기존 정책, 이전 결정과 이유를 다시 설명해야 한다.
문서와 이슈에 기록이 있어도 현재 요청과 연결해 읽지 않으면 같은 설명과 질문이 반복된다.

where-were-we가 기존 자료와 직접 작성한 맥락을 연결하고, AI가 요청에 필요한 근거를 찾아 읽도록 한다.
사용자는 근거와 선택의 영향을 보고 판단하며, AI에게 맡길 범위를 정한다.
AI가 자료를 찾거나 연결했다고 사용자의 결정·실행 승인을 대신하지 않는다.

장기적으로 AI가 역할을 나누어 IT 업무를 이어갈 수 있는 기반을 지향한다.
이번 기능은 그중 맥락의 연결·유지·조회에 해당한다.
모델 라우팅, 통합 인증, 에이전트 간 작업 배정·상태 통신을 구현하는 계획까지 확정한 것은 아니다.

## 기존 코드에서 확인한 출발점

아래는 기준 코드에서 읽은 내용이다. 설치 앱의 실제 동작을 검증한 결과는 아니다.

| 실제 코드 이름 | 확인한 내용 | 이번 기능에서 검토할 연결 |
|---|---|---|
| [ui/index.html](../ui/index.html)의 `featureContext`, `featureCopyText` | 선택한 기능의 관계와 연결된 작업을 표시하고 복사할 내용을 만든다 | 기능·화면의 관련 컨텍스트 표시와 전달 |
| [ui/index.html](../ui/index.html)의 `pill` 표시 | 이슈·PR 등을 작은 태그 형태로 표시한다 | 관련 컨텍스트 태그의 표현 |
| [project.py](../project.py) | 프로젝트 설정과 저장된 데이터를 화면·MCP에서 읽는 구조를 제공한다 | 화면 편집과 AI 조회가 같은 내용을 사용하도록 연결 |
| [mcp_server.py](../mcp_server.py)의 `find` | 화면·서버 기능·데이터와 이슈·PR의 제목·번호 등을 찾는다 | 배경·결정·문서 조회로 확장할 경계 |
| [briefing.py](../briefing.py)의 `request`, `source`, `view` | 수집 근거를 전달하고 저장된 설명의 상태를 조회한다 | 출처와 확인 시점을 유지하는 기존 방식 검토 |

관련 코드가 있다는 이유만으로 원하는 기능이 이미 구현돼 있다고 판단하지 않는다.
기존 검색은 요청의 의미를 이해해 관련 컨텍스트를 찾는 기능의 완료 근거가 아니다.

## 확정한 사용자 흐름

1. AI가 요청과 관련된 자료를 찾아 후보를 제안한다.
2. 후보마다 제목, 관련 있는 이유, 출처를 보여준다.
3. 사용자가 선택한 후보만 해당 대상의 관련 컨텍스트로 등록한다.
4. 평소에는 본문을 펼치지 않고 `관련 컨텍스트` 아래에 태그로 표시한다.
5. 태그를 열면 내용을 확인한다. 외부 자료는 원문으로 이동하고, 직접 작성한 내용은 앱 안에서 수정한다.
6. 다음 작업에서 AI는 연결된 컨텍스트를 찾아 읽는다.
7. 세션이 바뀌어도 연결을 유지하며 같은 연결을 매번 다시 승인받지 않는다.

표시 예시의 항목 이름은 가상 예시다.

```text
관련 컨텍스트  [서비스 사용자] [기능 정책] [관련 API]
```

후보를 찾기 위해 읽은 자료와 사용자가 연결한 자료를 구별한다.
자료를 연결한 행위는 관련성을 선택한 것이며, 그 안의 제안이나 명령을 승인한 것이 아니다.

## ADR-001: 기존 where-were-we를 확장한다

상태: 결정됨.

문제: 기록을 더 남겨도 다음 요청에서 찾아 쓰지 못하면 반복 설명이 줄지 않는다.

| 검토한 방법 | 사용자의 부담 | 만들고 유지할 부분 |
|---|---|---|
| 기존 기록을 필요할 때마다 직접 찾아 전달 | 요청마다 자료를 찾아 설명해야 한다 | 기존 기록 체계 |
| where-were-we에 맥락 연결과 조회를 추가 | 관련 자료를 선택하고 필요한 내용을 수정한다 | 기존 화면·프로젝트 데이터·AI 연결의 확장 |
| 별도의 범용 AI 조직 플랫폼을 구성 | 새 체계와 기존 작업의 관계를 관리한다 | 별도 작업·역할·상태 관리와 자료 연결 |

선택: where-were-we를 확장한다.
이유: 이미 있는 프로젝트·기능·작업 연결을 출발점으로 반복 설명 문제를 다룬다.

처음에는 실제 사용자의 작업에서 필요한 동작을 기준으로 만든다.
오픈소스라는 이유만으로 프로젝트마다 같은 문서 이름이나 기록 방식을 강제하지 않는다.
사용자별 자료 위치와 출처를 연결할 수 있어야 한다.

감수하는 한계: 현재 사용 방식에 대한 적합성은 확인할 수 있어도 다른 모든 프로젝트에 대한 적합성을 보장할 수 없다.
별도 조직 플랫폼과 기존 where-were-we의 실행 성능을 비교한 결과에 따른 선택은 아니다.

## ADR-002: 기존 자료는 원문에 연결하고, 원문이 없는 내용은 직접 편집한다

상태: 결정됨.

문제: 각 프로젝트의 결정 기록·API 문서·이슈를 복사하면 같은 내용의 수정 위치가 여러 곳으로 나뉜다.
반대로 링크만 허용하면 아직 문서가 없는 맥락을 적고 수정할 곳이 없다.

| 검토한 방법 | 얻는 것 | 부담·제약 |
|---|---|---|
| 모든 내용을 앱으로 복사 | 앱에서 내용을 한꺼번에 다룬다 | 원문과 사본이 달라질 수 있어 대조가 필요하다 |
| 링크만 등록 | 원문이 기준으로 유지된다 | 원문이 없는 내용을 앱에서 관리할 수 없다 |
| 원문 링크와 직접 작성을 함께 지원 | 기존 기록을 유지하면서 없는 맥락도 작성한다 | 두 종류의 수정 위치를 구분해야 한다 |

선택: 원문 링크와 직접 작성을 함께 지원한다.

- 기존 문서·이슈·PR은 원문이 기준이다.
- 직접 작성한 내용은 where-were-we가 기준이며 앱 안에서 수정할 수 있다.
- 어디에서 수정하는 내용인지 화면과 AI 조회 결과에서 구분한다.
- 원문 링크의 등록만으로 내용을 읽었다고 판단하지 않는다.
- 검색이나 표시를 위한 사본을 저장하더라도 원문과의 관계를 유지한다.

감수하는 한계: 원문 접근 권한과 형식에 따라 읽을 수 있는 범위가 달라진다.
지원할 출처 종류, 인증 방식, 내용 보관 방식은 구현 전에 정해야 한다.

## ADR-003: AI는 후보를 제안하고 사용자가 연결한다

상태: 결정됨.

문제: 사람이 모든 자료를 직접 찾으면 반복 작업이 남고, AI가 자동으로 확정하면 잘못 연결한 자료를 작업 근거로 삼을 수 있다.

| 검토한 방법 | 사용자의 할 일 | 영향 |
|---|---|---|
| 사용자가 직접 찾아 연결 | 자료 탐색과 관련성 판단 | 연결을 직접 통제하지만 탐색 부담이 남는다 |
| AI가 후보를 찾고 사용자가 선택 | 후보의 이유와 출처를 보고 선택 | 탐색 부담을 줄이고 연결 결정은 유지한다 |
| AI가 자동 연결하고 사용자가 수정 | 잘못된 연결을 사후 수정 | 손은 덜 가지만 잘못된 연결이 먼저 사용될 수 있다 |

선택: AI 후보 제안 후 사용자 선택.
이유: 자료를 찾는 부담을 줄이면서 어떤 근거를 연결할지 사용자가 정한다.

선택하지 않은 후보를 확정된 연결처럼 표시하거나 전달하지 않는다.
이미 선택한 연결은 유지하며 세션마다 재선택하게 하지 않는다.
사용자가 수동으로 기존 항목을 연결하거나 새 자료를 등록하는 경로도 유지한다.

감수하는 한계: 후보를 검토하는 수고는 남는다. 검색 정확도와 후보 제안 비용은 아직 측정하지 않았다.

## ADR-004: 평소에는 관련 컨텍스트 태그로 표시한다

상태: 결정됨.

선택: 화면의 이름은 `관련 컨텍스트`로 하고, 평소에는 이슈 태그처럼 간결하게 표시한다.
내용은 태그를 열었을 때 확인한다.

이유: 문서 본문을 늘 펼쳐 두지 않고도 어떤 배경과 근거가 연결됐는지 알 수 있어야 한다.
이 표시 방식은 사용자가 제안하고 확정했다. 별도 화면 시안 비교나 사용성 시험은 아직 하지 않았다.

감수하는 한계: 태그 이름만으로 자료 전체의 조건을 알 수 없다.
AI는 태그 이름만 보고 내용을 추정하지 않고 해당 자료를 읽어야 한다.
정확한 배치와 펼치는 방식은 기존 화면에 대조해 정한다.

## ADR-005: 맥락을 기억하되 판단과 실행 승인을 구분한다

상태: 원칙 결정됨. 저장 항목과 갱신 방법은 구현 설계가 필요함.

- 사용자의 명확한 결정, AI의 제안, 미확인 내용을 구별한다.
- 질문을 결정으로 저장하지 않는다. 짧은 동의는 무엇에 동의했는지 명확할 때만 반영한다.
- 맡긴 범위 안의 명확한 결정과 확인한 사실은 반영하고 변경 내용을 간단히 알린다.
- 모호하거나 기존 결정과 충돌하면 사용자에게 확인한다.
- 이전 선택을 바꾸면 변경 이유와 이전 근거를 따라갈 수 있게 한다.
- 결정됨·구현됨·검증됨·배포됨을 구분한다.
- 개인 맥락과 공유 프로젝트 자료의 범위를 구분한다.
- 사용자가 먼저 생각하고 판단할 수 있도록 AI는 근거와 선택의 영향을 준비한다.

컨텍스트 연결 승인과 내용 갱신은 다른 동작이다.
내용이 갱신됐다고 AI가 새 대상에 태그를 자동 확정해 붙이는 권한이 생기지 않는다.
이 기능이 새로운 업무 실행 권한을 부여하지 않는다.

## 구현 검토안과 아직 정하지 않은 것

아래 항목은 확정 결정과 구분한 구현 검토안이다.

- 같은 컨텍스트를 여러 대상에 연결하되 내용은 한 곳에서 관리한다.
- 태그 제거는 연결 해제로 다루고 원문 삭제와 구분한다.
- 원문 변경 시 바뀐 내용을 조회하고 이전 판단과의 충돌을 드러낸다.
- 읽지 못한 자료는 상태를 표시하고 읽은 근거처럼 사용하지 않는다.
- 직접 작성한 내용의 수정은 다음 AI 조회에 반영한다.
- 직접 작성한 내용을 외부 문서로 옮길 때는 정본 위치를 바꾸는 방식을 검토한다.
- 수정 주체, 이력, 복구 방식과 원문 확인 날짜·버전을 어떻게 보여줄지 정한다.

구현 전에 결정할 사항:

- 태그를 붙일 대상의 범위와 식별 방법: 프로젝트·기능·화면·작업 사이의 관계.
- 연결된 문서 전체와 필요한 부분 중 무엇을 언제 읽을지, 원문 변경을 어떻게 확인할지.
- 링크·로컬 문서 등 지원 출처의 범위와 접근 방법.
- 후보 검색 방법, AI 호출 시점, 비용 표시와 사용 한도.
- 직접 작성한 내용과 연결의 저장 위치, 편집 충돌 처리, 자료 범위 구분.
- AI에게 제공할 조회 도구와 기존 세션 시작·요청 흐름의 연결 방법.

벡터 데이터베이스, 검색 모델, 새 서버, 특정 파일 형식은 선택하지 않았다.
기존 구조를 읽고 대안을 비교한 뒤 정한다.

## 완료 조건과 확인 방식

아래는 기능 구현 시 확인할 조건이다. 현재 전부 미검증이다.
문서 작성이나 기존 코드 확인만으로 체크하지 않는다.

| 완료 조건 | 확인 방식 |
|---|---|
| AI가 제목·관련 이유·출처가 있는 후보를 제안한다 | 테스트 코드로 후보 구조와 출처 연결을 확인 |
| 선택한 후보만 관련 컨텍스트로 연결한다 | 선택·미선택·중복 선택 경로를 테스트 코드로 확인 |
| 새 세션에서도 선택한 연결을 다시 사용할 수 있다 | 저장 후 새 조회에서 연결 유지 여부를 테스트 코드로 확인 |
| 연결된 내용과 후보, 결정과 제안을 구분한다 | 조회 결과와 상태 전환을 테스트 코드로 확인 |
| 직접 작성한 내용을 수정하면 다음 조회에 반영된다 | 편집·저장·재조회 경로를 테스트 코드로 확인 |
| 원문을 읽지 못하거나 오래된 근거이면 그 상태를 알 수 있다 | 실패·변경된 출처를 가짜 입력으로 주어 확인 |
| 개인 맥락이 공유 프로젝트 조회에 섞이지 않는다 | 자료 범위를 달리한 조회를 테스트 코드로 확인 |
| 새 AI 세션이 연결된 배경을 활용해 반복 질문을 줄인다 | 대표 요청으로 사용 흐름을 확인하고 반복 설명·잘못된 근거를 기록 |
| 태그 선택·열기·직접 편집 흐름을 화면에서 이해할 수 있다 | 실제 앱에서 사람이 확인하며 WebKit 레이아웃도 확인 |
| 필요한 외부 자료를 실제 계정으로 읽을 수 있다 | 지원 출처가 정해진 뒤 필요한 실제 연결을 확인 |

검사 작성 시에는 실패하는 입력을 먼저 확인하고, 구현 뒤 같은 동작이 통과하는지 대조한다.
자동 검증에서는 실제 AI 호출과 과금을 차단한다.
실제 AI·외부 계정이 필요한 확인은 사용자에게 맡겨진 범위와 계정을 확인한 뒤 진행한다.

## 현재 저장 범위와 이어서 할 지점

이번 변경은 이 문서와 ADR을 브랜치에 보존하는 문서 작업이다.
기능 코드, 저장 형식, 조회 도구, 편집 화면은 구현하지 않았다.
문서 전용 변경이므로 기능 테스트를 작성하거나 실행하지 않는다.

이어서 할 때는 기존 기능·화면·프로젝트 데이터의 식별과 저장 경계를 읽고,
태그를 붙이는 대상과 자료 조회 방법의 대안을 비교한다.
확정된 결정은 다시 처음부터 묻지 않고, 구현 선택에 필요한 부분만 확인한다.
다른 작업 폴더에서 진행 중인 미커밋 변경을 이 작업에 포함하지 않는다.
